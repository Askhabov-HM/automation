# PDF Documents

Самодостаточный переносимый навык `$pdf-documents`. В этой папке находятся `SKILL.md`, скрипты, оба оформления, ресурсы, примеры, эталоны и тесты. Глобальная установленная копия работает независимо от исходного Git-репозитория.

**Режим по умолчанию — Economy.** Technical включается только по явному запросу пользователя. Если нужны оба, навык выполняет две сборки из одного содержимого. Согласование текста само по себе не меняет режим.

## Установка глобального навыка и перенос на другой компьютер

После получения репозитория через Git из его корня:

```powershell
python pdf/scripts/install_skill.py --setup
```

Нужны Python 3.11+ и интернет для первой установки Python-зависимостей. Установщик копирует весь пакет в каталог `skills/pdf-documents` внутри `CODEX_HOME` (по умолчанию `~/.codex`), затем создаёт отдельное окружение. Для обнаружения современными клиентами также создаётся ссылка `~/.agents/skills/pdf-documents` на эту глобальную копию. Она не ссылается на Git-репозиторий. Существующий другой навык не перезаписывается.

Заново копировать виртуальное окружение, кеш или исполняемые файлы со старого компьютера не требуется. PDFium устанавливается из закреплённых Python-зависимостей; свободные DejaVu Sans/Mono и их лицензия уже включены. Poppler поддерживается дополнительно. На текущем компьютере системные Arial/Consolas сохраняют выбранный вид; на другом устройстве доступны комплектные DejaVu.

После установки можно обращаться к `$pdf-documents` в любом проекте: «создай PDF» означает Economy; «создай PDF Technical» означает техническое оформление. При необходимости перезапустите сессию Codex для обновления списка навыков.

Проверка совпадения с Git-копией и обновление:

```powershell
python pdf/scripts/install_skill.py --check
python pdf/scripts/install_skill.py --update --setup
```

Обновление сохраняет рабочие входные данные, результаты и образцы. Оно останавливается, если установленные исходники навыка изменены вручную. Для другого каталога навыков можно передать `--skills-dir`; при явном выборе каталога автоматическая ссылка обнаружения не создаётся. В Git хранятся только переносимые исходники, ресурсы и тесты; машинные зависимости создаются заново.

Дальнейшие команды в этом руководстве выполняются **из корня пакета**, то есть из `automation/pdf` или установленного `pdf-documents`.

Два согласованных режима подготовки документов:

- **Economy** — чёрный текст на белом A4, без фотографий и графиков. Для разработки и согласования содержания. Данные графиков, подписи изображений и строки таблиц остаются текстом.
- **Technical** — деловой технический стиль: Arial/DejaVu Sans, нумерованные разделы, моноширинные служебные подписи, тонкая сетка таблиц, сдержанная палитра. Фото и векторные графики добавляются по содержимому.

Выбранные пользователем образцы сохранены в `references/00-economy-text.pdf` и `references/05-technical.pdf`. Они задают оформление. Новые документы не ограничены тремя или десятью страницами.

## Запуск

Для запуска непосредственно из папки пакета, один раз:

```powershell
python scripts/pdf_tool.py setup --renderer pdfium
```

Создаются `.venv` и кеш пакетов. Версии прямых и транзитивных зависимостей закреплены в `requirements.txt`. PDFium доступен после установки зависимостей, отдельная системная установка рендерера не обязательна. Если предпочтителен Poppler, его можно указать через `setup --pdftoppm "C:/path/to/Library/bin/pdftoppm.exe"`. Автоматической загрузки произвольных исполняемых файлов нет.

Далее каждая команда сама использует окружение `.venv` текущей копии пакета:

```powershell
python scripts/pdf_tool.py build examples/demo.json --name demo
python scripts/pdf_tool.py build examples/demo.json --mode technical --name demo
```

Одна команда создаёт PDF, проверяет содержимое, рендерит страницы, сравнивает их с одобренным образцом и готовит обзорные изображения. При ошибке она останавливается с кодом 1. Успешная сборка, в том числе ожидающая визуального просмотра, возвращает код 0.

Команды работают из любого каталога при передаче корректных путей к скрипту и содержимому. `--name` — постоянный идентификатор документа, например `demo`, `project-brief` или `requirements`. Пара режимов и имён имеет отдельные результаты и отдельный образец.

## Содержимое отдельно от оформления

Для простого текста поддерживается Markdown: `#` задаёт название, `##` — разделы, пустые строки — абзацы, `-` — пункты. Это намеренно небольшой текстовый формат, не полноценный Markdown-движок. Остальная разметка выводится буквально.

Для фото, графиков и таблиц используйте JSON. Полный пример: `examples/demo.json`. Строки рассматриваются как текст, не как исполняемая разметка.

```json
{
  "title": "Пример документа",
  "subtitle": "Краткое описание",
  "cover": true,
  "sections": [
    {
      "title": "Первый раздел",
      "kicker": "Описание",
      "page_break": true,
      "blocks": [
        {"type": "paragraph", "text": "Содержимое документа."}
      ]
    }
  ]
}
```

Блоки:

| Тип | Поля |
|---|---|
| `paragraph`, `heading`, `quote` | `text` |
| `list` | `items`: массив строк |
| `callout` | `title`, `text` |
| `link` | `text`, `url` с HTTP(S) |
| `image` | `source`: локальный файл относительно JSON; `caption`; необязательные `credit`, `url`, `height` |
| `chart` | `kind`: `line`, `bars`, `donut`; `labels`, `values`; необязательные `x_label`, `y_label`, `text` |
| `table` | `columns`, `rows`; необязательные положительные пропорции `widths` и индекс `delta_column` для выделения разницы цветом (с нуля) |

Technical учитывает `cover` и `page_break`. Economy игнорирует декоративную обложку и принудительные разрывы разделов, чтобы текст был компактнее. Длинные таблицы Technical разделяются автоматически, строки сохраняются целиком, заголовок повторяется. Недопустимые данные останавливают сборку.

Системные Arial + Consolas используются при наличии; иначе доступны включённые DejaVu Sans + Mono. Шрифты кешируются локально; Windows-шрифты не распространяются в Git. Для своего каталога используйте `--font-dir`. Изображения задаются локальными файлами: инструмент не скачивает URL из документа; внешние URL остаются ссылками на источники.

## Короткий JSON и подробные логи

Нормальный вывод команды — один JSON-объект на одной строке, без текста документа и трассировок. Основные поля:

- `status`: `failed`, `needs_visual_review`, `passed`;
- `checks_passed`, `pages`, `run_id`;
- `review_pages`, `removed_pages`;
- `cache`: попадания кеша изображений и рендера;
- `files`: PDF, подробный отчёт, локальный лог, обзорные изображения и подсвеченные различия.

Ошибка содержит `stage`, `errors[].code`, короткое объяснение и, при наличии, путь к логу. Текст исключений и диагностика библиотек остаются в локальном `build.log`. Подробный отчёт проверки — `report.json`. `status` показывает результат последней успешной сборки:

```powershell
python scripts/pdf_tool.py status --name demo --mode technical
```

Каждая сборка имеет собственный каталог `output/<name>/<mode>/<run_id>/`. Неудачная сборка не перезаписывает предыдущий результат. После неудачи ориентируйтесь на JSON ошибки текущей команды, а не на `status` предыдущей успешной сборки.

## Кеш

- `.venv/`: отдельное окружение; во время сборки версии сверяются с `requirements.txt`.
- `.cache/pip/`: повторное использование загруженных пакетов.
- `.cache/poppler/`: дополнительный переносной Poppler на Windows; PDFium входит в Python-окружение.
- `.cache/fonts/`: копии шрифтов по SHA-256 исходных файлов.
- `.cache/images/`: копия исходного изображения и версия до 1600 пикселей. Ключ включает содержимое, параметры обработки и версию Pillow. Изменённый или повреждённый кеш восстанавливается из исходника.
- `.cache/renders/`: PNG по содержимому PDF, версии рендерера и DPI; хеши страниц проверяются перед повторным использованием.

Для диагностики можно принудительно пересоздать рендер: `build ... --no-render-cache`. Кеш восстанавливаемый; исходные ресурсы сохраняйте в `assets/` или рядом с документом.

## Сравнение и одобрение

Одобренные версии находятся в `baselines/`, отдельно от `.cache/`. Это важное состояние проверки, а не удаляемый кеш. Они не создаются автоматически. Выбранные эталоны оформления в `references/` не означают, что содержание любого нового документа уже одобрено.

При первой сборке необходимо просмотреть все страницы. Затем сравниваются точные RGB-пиксели с последней одобренной версией. При изменении шаблона, шрифтов, DPI или рендерера требуется полный просмотр. Удалённые страницы отмечаются отдельно. Проверки всего текста, формата, шрифтов и полей выполняются при каждой сборке, даже если просмотр нужен только для изменившихся страниц.

Сначала откройте `files.previews`, при необходимости полные `pages/page-*.png` и `files.diffs`. Отличие не означает ошибку; совпадение с образцом не подтверждает правильность новых чисел или выводов. Изменение общего дизайна требует полного визуального просмотра, даже если автоматическое сравнение выделяет только часть страниц.

**Только после фактического просмотра и явного одобрения пользователем** конкретной сборки:

```powershell
python scripts/pdf_tool.py approve --name demo --mode technical --run RUN_ID --reviewed-pages all
```

Вместо `all` можно указать просмотренные страницы, например `1,3`. Все `review_pages` должны быть подтверждены. При удалении страниц дополнительно нужен `--acknowledge-removed-pages`. `RUN_ID` берётся из JSON той сборки, которую одобрили. Команда проверяет, что PDF и PNG не изменились после проверки.

`passed` появляется после явного подтверждения просмотра либо когда новая сборка полностью совпадает с уже одобренными страницами при тех же настройках. Повреждённый образец блокирует сравнение; его нельзя молча заменять новой сборкой.

## Хранение

В Git: `templates/`, `references/`, `scripts/`, `tests/`, `examples/`, исходные ресурсы и этот файл. Примеры содержат только демонстрационные данные.

Локально и вне Git: `output/`, `baselines/`, `.cache/`, `.venv/`, `tmp/`, а также `inputs/` для личных рабочих документов. Резервные копии важных одобренных версий делаются отдельно от очистки кеша.

Входная инструкция навыка — `SKILL.md` рядом с этим руководством. Она закрепляет выбор режима, порядок проверки и условия обновления образца. Результаты и ссылки из JSON относятся к этой папке пакета; глобальная копия не обращается к исходной папке `automation/pdf`.

## Проверка реализации

```powershell
.venv/Scripts/python.exe -m unittest discover -s tests -v
```

На Linux используйте `.venv/bin/python`. Тесты создают изолированные временные модули и не одобряют рабочие документы. Они проверяют JSON, две стадии проверки, повторное использование и восстановление кеша, изменение одной страницы, удаление страниц, повтор заголовка длинной таблицы и целостность образца. Отдельно проверяются переносимая установка, запуск Economy по умолчанию, Technical по запросу и рендер PDFium с комплектными шрифтами.
